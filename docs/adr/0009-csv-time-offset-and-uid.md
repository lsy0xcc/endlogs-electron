# ADR-0009：导出时间列带显式 +08:00 偏移；文件名附带角色 UID

- 状态：已接受（2026-11-20，用户决策）；时间列时区被 ADR-0012 修订（跟随系统时区）、列结构被 ADR-0013 修订（v2 十列，后再度修订为 camelCase 11 列）、**显式偏移方案被 ADR-0013 二次修订取代**（无偏移 `time` 列仅人读 + `isoTime` UTC 权威列）。文件名附 UID 的决策不变
- 修订：ADR-0004 中「与旧项目格式完全一致（仅加 BOM）」的表述——列结构仍一致，但时间列格式与文件名有变

## 背景

用户提出导出改为 UTC 以获得自描述性与来源可区分性。讨论结论：UTC 会让 CSV 中每行时间与游戏内显示差 8 小时（用户是国服玩家，Excel 对照游戏记录时需心算），代价大于收益。

## 决策

1. **导出时间列**：`YYYY-MM-DD HH:MM:SS+08:00`——显式偏移（自描述、可区分来源），且数值与基准时区/游戏内显示一致
2. **导出文件名**：`endfield_{type}_{start}_{end}_uid{roleId}.csv`——UID 供导入时预选账号
3. **导入侧**：时间列含偏移 → 按偏移解析（本项目文件）；纯格式 → 用户可选时区、默认 Asia/Shanghai（旧 Python 项目文件）；混用两种格式视为非法文件
4. **归属账号**：导入时用户显式选择（默认当前账号），文件名 UID 命中已知账号时预选；不做静默自动分配（错配会污染流水库）

## 后果

- 与旧格式的差异从「仅 BOM」扩大为：时间列偏移 + 文件名后缀。旧项目不消费 CSV，实际互操作面（本项目导入旧导出）不受影响
- Excel 可能将时间列识别为文本（不识别为日期类型）；ISO 格式字典序 = 时间序，排序可用。接受
- 拒绝 UTC 方案的原因记录在案：与游戏内时间差 8h，对人不可读
